# ChessEngine

Stockfish compiled into the app process, behind the Swift API declared in
`Sources/ChessEngine/`: `StockfishEngine`, `SearchLimit`, `EngineScore`, `EngineInfo`,
`EngineResult` and `EngineEvent`. (The module contract that specifies them is
`docs/ARCHITECTURE.md`, a development document that is not part of the published source, so
this file is written to stand on its own.)

```swift
let engine = StockfishEngine.shared
try await engine.prepare()                        // optional; analyze() prepares on demand
for try await event in await engine.analyze(fen: fen, limit: .movetime(milliseconds: 3_000)) {
    switch event {
    case .info(let info): updateEval(info)         // depth, score, pv, nodes, nps, multiPV
    case .bestMove(let result): showArrow(result.bestMove)
    }
}
```

## Stockfish version

- Release **Stockfish 19** (tag `sf_19`, published 2026-09-05), the latest non-development
  release when vendored on 2026-09-13.
- Tarball `https://github.com/official-stockfish/Stockfish/archive/refs/tags/sf_19.tar.gz`,
  SHA-256 `519b653d0d1ffb96531d982ccbe5c6a19425e8388e0e3c2f70f34b424ab32d76`.
- `StockfishEngine.shared.version` returns `"Stockfish 19"`.

### Network

Stockfish 19 uses a single network (`EvalFileDefaultName` in `src/evaluate.h`; the separate
Big and Small networks of 17.x are gone):

| File | Size | SHA-256 |
| --- | --- | --- |
| `nn-1a298aa575a0.nnue` | 98,511,183 bytes (94.0 MiB; about 79 MB compressed) | `1a298aa575a085434d29027978dc36867fe9c5bcea9376654b7a8eba1e52dfc2` |

The full SHA-256 is pinned in `scripts/fetch-nets.sh` (`pinned_sha256`), which rejects any
download that does not match it exactly. The 12 hex digits in the file name are only a
48-bit prefix of the hash, so the script uses them just as a sanity check on the pin.

The file is a regular SwiftPM resource, loaded from `Bundle.module` at runtime. Stockfish
is compiled with `NNUE_EMBEDDING_OFF`, so nothing is embedded with incbin. It is below
GitHub's 100 MB hard limit, so it can be committed as an ordinary git object; otherwise run
`scripts/fetch-nets.sh` after cloning.

### Local modifications (GPLv3 section 5a notice)

`patches/0001-optional-no-system-wide-shm.patch` (2026-09-13): lets an embedding
application define `STOCKFISH_NO_SYSTEM_WIDE_SHM` to turn off Stockfish's cross-process
shared-memory network store. On Apple platforms that store creates `/tmp/stockfish-<uid>`,
a Unix-domain socket server thread per network copy, and an `atexit` handler. With the
define, the network lives in ordinary process memory, which is Stockfish's existing
fallback path. Without the define the source behaves exactly like upstream.

### Upgrading

1. Set `SF_TAG` and `SF_TARBALL_SHA256` in `scripts/vendor-stockfish.sh`, run it.
2. If `src/evaluate.h` names a new network, pin its full SHA-256 in `pinned_sha256()` in
   `scripts/fetch-nets.sh` and in the Network table above (the script's error message says
   how to obtain the hash), then run `scripts/fetch-nets.sh` (it also deletes networks the
   new release no longer uses).
3. If a patch no longer applies, update it. Check `src/engine.h` for API changes to the
   callbacks used in `sf_bridge.cpp`.
4. `swift test`, then both `xcodebuild` builds below.

## How Stockfish is called

The bridge uses Stockfish's in-process C++ API (`Stockfish::Engine`: `set_position`, `go`
with `Search::LimitsType`, `stop`, `set_on_update_full`, `set_on_bestmove`, options through
`OptionsMap`). There is no UCI text protocol, no pipes and no redirection of stdout. The C
interface in `CStockfish.h` keeps Swift/C++ interoperability out of the app target.

- **Network loading.** `Engine(path)` treats `path.parent_path()` as its binary directory and
  loads the default network from there during construction, so the bridge passes
  `<bundle>/NNUE/stockfish` and the network loads without setting `EvalFile`.
- **No `exit()`.** Stockfish calls `exit()` right after reporting a network that failed to
  load. The bridge's network-verification callback throws a C++ exception for error
  messages, so `exit()` is never reached and `prepare()` throws
  `EngineError.engineUnavailable` instead. Stockfish is compiled with C++ exceptions enabled
  for this (its Makefile uses `-fno-exceptions`). A test creates an engine from a missing
  directory to prove the process survives.
- **No stdout.** Every engine callback (info, no-moves info, iteration, start, best move,
  network verification) is installed, and no option-info listener is installed, so the
  engine prints nothing during normal use. Checked in an iOS simulator app: the console
  shows only the app's own output. The remaining writes in Stockfish are on paths the
  bridge never takes (tablebases, unknown option names, trace and benchmark commands) or
  go to stderr right before an `exit()` on out-of-memory or thread-creation failure (see
  caveats).
- **Search lifecycle.** One engine instance serves the whole app session. Blocking calls
  (create, resize, start) run on one serial dispatch queue. Stop is an atomic flag and works
  from any thread. Each search has an id, so a late stop request cannot stop a newer search.
- **New analysis while one runs.** The running search is stopped (as with `stop()` below) and
  its stream still ends with `.bestMove` (the best move so far), then the new search starts.
- **Consumer cancellation.** Cancelling the task that iterates a stream stops that search.
- **`stop()`.** Returns immediately; the stream delivers `.bestMove` and finishes (0.1 to
  15 ms after the call in the Mac tests, depending on machine load). The stop is held back
  until the search has completed its first depth, which takes milliseconds: Stockfish
  stopped before that has scored no root move and reports the first legal move in
  move-generation order (for example `a2a3`) with score 0 and an empty PV. A stop that
  arrives before the search has started also turns it into a depth-1 search. So a stopped
  stream always ends with a searched best move, and `lastInfo.pv.first` equals it, even
  when `stop()` directly follows `analyze()` or lands while the engine is still loading.
  Consumer cancellation is not held back.
- **Streams.** Unbounded buffering. `.info` for every principal-variation report, including
  reports whose score is only a lower or upper bound (Stockfish emits every multiPV line in
  each batch, and its final report can be a bound, so dropping them would leave `lastInfo`
  or a multiPV line pointing at an older PV). `EngineResult.lastInfo` is the last report of
  line 1 and its `pv.first` equals `bestMove`.
- **Errors.** `EngineError.invalidPosition` (Stockfish's own FEN validation: malformed FEN,
  wrong number of kings, pawns on the first or eighth rank, too many pieces; plus two checks
  in the bridge that Stockfish's parser lacks and its search needs: the side not to move in
  check, more than two checkers),
  `.invalidLimit`, `.networkMissing`, `.engineUnavailable`, and `.noLegalMoves` for
  checkmate or stalemate (after a depth-0 `.info` with `mate(0)` or `centipawns(0)`).
- **Scores** are from the side to move's point of view. Mate scores are in moves
  (`mate(1)` = mate in one, negative = getting mated), converted exactly like Stockfish's
  UCI output.

### Defaults

- Threads: `sysctl hw.perflevel0.physicalcpu` (the fastest core cluster), falling back to
  `activeProcessorCount - 1`. That is 2 on current iPhones and 6 on an M5 Max Mac.
- Hash: 128 MB, or 64 MB when physical memory is below 3.5 GiB. iOS reports somewhat less
  than the installed RAM as physical memory, so a literal 4 GB cut-off could put 4 GB
  iPhones in the low-memory group; 3.5 GiB separates 3 GB devices from 4 GB devices.
  Check `ProcessInfo.processInfo.physicalMemory` on a 4 GB device to confirm.
- The transposition table is kept between searches.

### Caveats for the app

- **Remaining `exit()` paths.** Stockfish still exits the process if allocating the network,
  the hash table or per-thread search state fails, or if a search thread cannot be created.
  On iOS the memory limit would normally terminate the app first.
- **Memory.** See Measurements: plan for roughly 300 MB while an engine exists and about
  110 MB more during `prepare()`. There is no API to unload the engine; call `prepare()`
  when analysis is about to be needed rather than at launch.
- **Threads.** Only the performance cluster is used (2 threads on iPhones). Efficiency cores
  would add speed but also heat on long think times.
- **Backgrounding.** iOS suspends the app's threads in the background, which freezes a
  running search and its movetime clock. Stop or restart the analysis on scene-phase
  changes.
- **Validate before analyzing.** The bridge rejects positions that would crash Stockfish, but
  not all illegal ones (for example impossible pawn structures). Run ChessCore's
  `Position.validate()` first and show its issues to the user.
- **UCI castling** is standard (`e1g1`, `e1c1`), never king-takes-rook.
- **Transposition table** entries persist between analyses of different screenshots. That is
  harmless for correctness (entries are keyed by position) but means a repeated analysis of
  the same position is faster and can reach a greater depth than the first.

## Build flags

Architecture switches are in `Sources/CStockfish/bridge/sf_build_config.h`, force-included
into every Stockfish file, because SwiftPM cannot vary flags per architecture and the
"generic iOS Simulator" destination builds arm64 and x86_64 in one go.

| Setting | Value | Reason |
| --- | --- | --- |
| arm64 | `IS_64BIT`, `USE_POPCNT`, `USE_NEON=8` | Equivalent of Stockfish's `ARCH=armv8`. |
| NEON dot product | **off** | See below. |
| x86_64 (Intel Mac simulator only) | `IS_64BIT` | Portable build; only needs to be correct. |
| Optimization | `-O3 -funroll-loops`, all configurations | Makefile values. Forced in Debug too: an unoptimized engine is about ten times slower. |
| LTO | `-flto=full`, Release only | Makefile value. In Debug it would add about 10 s to every app link. |
| `NDEBUG` | Release only | Debug keeps Stockfish's assertions. |
| libc++ hardening | off | Xcode's Debug configuration enables libc++ debug hardening, which bounds-checks every `std::array` access in the search. |
| Exceptions | on | Needed to turn the fatal network error into a Swift error (see above). |
| `NNUE_EMBEDDING_OFF`, `STOCKFISH_NO_SYSTEM_WIDE_SHM` | defined | Network from the bundle; no `/tmp` shared memory. |

**Why no dot product.** Stockfish's `apple-silicon` and `armv8-dotprod` targets add
`-march=armv8.2-a+dotprod -DUSE_NEON_DOTPROD`. The app's deployment target is iOS 26, and
raising it there from iOS 18 did not make dot product safe: iOS 26 does drop the Apple A12
iPhones (iPhone XS, XS Max, XR), but the app is universal and iPadOS 26 still runs on A12
and A12X iPads (iPad 8th generation, iPad mini 5th generation, iPad Air 3rd generation, iPad
Pro 11-inch 1st generation, iPad Pro 12.9-inch 3rd generation). LLVM's CPU definitions give
`apple-a13` and later the dot-product extension but not `apple-a12` (checked with
`clang -mcpu=apple-a12 -dM -E`: no `__ARM_FEATURE_DOTPROD`), and an App Store app cannot
ship a separate slice per CPU. A dot-product build would crash with an illegal instruction
on those iPads. The cost is small: Stockfish's `bench` on this Mac measured the
dot-product build about 5 % faster in CPU time per node, within the noise of a heavily
loaded machine. Runtime dispatch (compiling the engine twice and picking a copy by
`hw.optional.arm.FEAT_DotProd`) would recover that if it ever matters.

Stockfish's `-mdynamic-no-pic` is not used (iOS requires position-independent code), and the
default `-mcpu` is kept (a per-architecture `-mcpu` would break the x86_64 simulator slice).

## Measurements (Apple M5 Max, macOS 26.6, 2026-09-13)

The machine was running unrelated jobs (load average 35 to 150 on 18 cores) during all
measurements, so the numbers below are lower bounds and vary between runs.

- **Nodes per second**, start position, 1 s movetime, default 6 threads, 128 MB hash:
  3.1 to 4.5 million (Release), best observed 5.0 million. Same position in a Release iOS
  app on the iPhone 17 Pro simulator (6 threads): 2.4 to 2.9 million.
- **Code size**: a Release iOS app binary grows by about 717 KB (799,520 vs 82,184 bytes for
  an otherwise empty SwiftUI app). The network adds 94 MB to the app bundle (about 79 MB
  compressed).
- **Memory**: the network object is 109 MB and each search thread about 29 MB, plus the hash
  table. Expect roughly 300 MB resident with 2 threads and 128 MB hash, and about 110 MB more
  during `prepare()` (Stockfish builds the network once and then copies it). The Mac figures
  are higher (435 MB with 2 threads) because macOS's allocator keeps the freed temporary
  network cached; measure on a device with Instruments before relying on the iOS figure.
- `prepare()` takes about 0.2 s (network load).

## Tests

```
swift test                                        # macOS, Debug
swift test -c release -Xswiftc -enable-testing    # macOS, Release flags
xcodebuild -scheme ChessEngine -destination 'generic/platform=iOS Simulator' build
xcodebuild -scheme ChessEngine -destination 'generic/platform=iOS' build
```

The suite covers: start position at 500 ms (legal UCI move, info with depth and score),
mate in one for white and for black (`d1d8` / `d8d1` with `mate(1)`), `stop()` during a
10 s search (best move within 500 ms), `stop()` right after `analyze()` (awaited, from another
task, with multiPV 3, on an analysis superseded at once, and on an engine that is still
loading its network; each must report the mating move with a non-empty PV rather than the
first generated legal move), five sequential analyses, a depth limit, multiPV 3,
a new analysis superseding a running one, consumer cancellation, invalid FENs, a
checkmated position, a missing network without process exit, and a 1 s nodes-per-second
report. Tests share `StockfishEngine.shared` and run serialized. On macOS, `FetchNetsScriptTests`
runs a copy of `scripts/fetch-nets.sh` in a temporary folder with a stub `curl`: the pinned
network is accepted, a file that matches only the 12-digit name prefix is rejected, and a
network without a pinned hash fails before anything is downloaded or deleted.

Diagnostics, off by default: `CHESSENGINE_BENCH=1` runs a single-thread nodes-per-CPU-second
benchmark (useful for comparing build flags on a busy machine) and
`CHESSENGINE_MEMORY=<threads>` prints the memory footprint of an engine with that many
threads.

## Alternative considered: chesskit-engine

[chesskit-app/chesskit-engine](https://github.com/chesskit-app/chesskit-engine) (0.7.0,
MIT wrapper, Stockfish 17 fork as a submodule) was not used:

- It talks UCI text: it calls `dup2` on the process's stdin and stdout to redirect them
  into pipes, which captures everything else the app prints and is process-global.
- Reading depends on `NSFileHandle` notifications on the main run loop.
- It lags upstream (Stockfish 17 fork, not 19) and ships Lc0 alongside.
- Networks still have to be supplied by the app.

## License obligations (GPLv3)

Stockfish is GPLv3 (`Sources/CStockfish/stockfish/Copying.txt`). It is statically linked into
the app binary, so the app as distributed is a combined work covered by GPLv3. This is a
summary for planning, not legal advice.

- **Source.** Whoever receives the app must be able to get the complete corresponding
  source of that exact binary under GPLv3: the whole app (Swift code, this package,
  `project.yml`, build scripts, and the Core ML model and whatever is needed to rebuild it),
  not only Stockfish. Usual practice: a public repository tagged per App Store release,
  linked from the app and the App Store description (GPLv3 section 6(d)).
- **Notices.** Show the GPLv3 text, Stockfish's copyright notice ("Copyright (C) 2004-2026
  The Stockfish developers (see AUTHORS file)"), and the no-warranty statement inside the
  app, for example on an About or Licenses screen. Keep `patches/` and the modification
  notice above.
- **Attribution for the network.** Stockfish's networks are trained on Leela Chess Zero data
  released under the Open Database License; credit it alongside Stockfish.
- **No further restrictions.** GPLv3 section 10 forbids imposing extra restrictions on
  recipients. Apple's standard App Store licence (usage rules, no redistribution) is widely
  considered incompatible with that; VLC was removed from the App Store in 2011 after a
  copyright holder objected. Several App Store apps ship Stockfish with their source
  published, and the Stockfish maintainers have enforced the GPL over missing source and
  notices rather than over App Store distribution itself (their 2021 case against ChessBase),
  but the incompatibility is a residual risk. Supplying a custom EULA in App Store Connect
  that grants GPLv3 terms for the app reduces it.
- **Charging** for the app or for in-app purchases is allowed. Anyone may rebuild and
  redistribute the published source, including the paywall code, without paying.
- **Trademark.** GPLv3 does not grant use of the Stockfish name or logo for branding.
  Describing the engine as "Stockfish 19" in credits is fine.
